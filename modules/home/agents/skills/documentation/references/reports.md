# Weekly and Status Reports

Give the intended reader an accurate view of progress, impact, decisions, and next actions. Establish the reporting period, timezone when boundaries matter, audience, repository scope, and available activity sources.

## Evidence

Inspect only relevant history, changes, tests, and supplied issue/PR/activity notes. Commit dates, author dates, merge dates, and deployment dates represent different events. Use the event appropriate to the report and state significant evidence limits.

Repository history can show code changes; it cannot alone prove hours worked, deployment, business impact, or the absence of blockers. Use supplied notes for work not visible in the repository. Preserve exact metrics and units with their source and period.

## Flexible Skeleton

1. **Period and Main Outcome.** Lead with what matters to this audience.
2. **Completed.** State supported results. Distinguish implementation, review, merge, release, and deployment when relevant.
3. **In Progress.** Include only supported ongoing work and remaining steps.
4. **Blocked or Needs a Decision.** Describe known blockers or questions; no evidence of blockers is not a verified "no blockers" claim.
5. **Next.** Separate supplied commitments from recommendations. An inferred next step is a suggestion, not the user's plan.

Group related work instead of listing every commit. Link important changes where the reader needs detail. If evidence covers only repository activity, label that scope clearly. Omit irrelevant sections while keeping consequential uncertainty visible.
